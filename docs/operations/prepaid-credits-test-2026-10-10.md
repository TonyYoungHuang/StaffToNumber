## 本轮发现并修复的问题

1. **消费终态可以被后续状态改写。** 原触发器可能把已消费改为释放，或把已释放改为消费。SQLite、PostgreSQL 生成器及独立迁移 SQL 统一限定 `status = 'reserved'` 才能变更账本；对两个任务族、迟到完成、重试和删除增加回归。
2. **叠加积分包隐藏旧会员期限。** 账户原实现优先返回永久预付权益，覆盖活跃旧套餐的期限与来源。现在保留活跃会员资料；旧期限过后才回落到预付的永久编辑权限。
3. **叠加积分包阻断旧会员导出。** 原限制根据“有预付积分”判断，会把仍有效的旧会员同步导出也阻断。改为只对当前权限来源是预付的账户要求渲染走队列；专门验证旧会员 PDF 权限。
4. **存储查询无法兼容 schema 25 Worker。** 新查询直接读取尚未迁移的积分表。现在先检查表是否存在，旧 schema 的存储解析不报错；同时验证预付存储与月度档位独立。
5. **PostgreSQL 迁移遗漏应用角色授权。** 新表和触发器函数未向运行角色授权，超级用户测试会掩盖故障。迁移增加 `runtime_role` 参数及明确授权，测试改用无管理权限的新应用角色执行登录、发码、兑换、任务预留、Worker 状态更新与删除。

### PostgreSQL 25 → 26 与并发

使用独立容器 `score-prepaid-qa-20261010`，仅绑定 `127.0.0.1:55432`。数据库数据目录挂载在 E 盘项目 `.tmp/prepaid-credits-2026-10-10/pgdata`；测试日志及 SQLite 临时数据也留在该任务目录。另建本地 Redis 容器 `score-prepaid-redis-qa-20261010`、端口 `56379` 执行真实 BullMQ 重试检查。

测试用代码生成旧账户、激活码、原文件、已有乐谱及旧任务，保留所有旧表的列、默认值、外键、索引和行，再移除新增预付表构造 schema 25。SQLite 通用导入器不翻译 CHECK，三条旧 CHECK 在导入后按 PostgreSQL DDL 恢复；额外设置旧四种月／年套餐白名单约束。使用本地合成资料，不读取生产客户数据。

以 owner 连续执行两遍 `prepaid-credit-packs.sql`，核对所有旧表的全部行仍完全一致，再通过独立无管理权限运行角色操作。测试覆盖同时首次登录只发放一次；预留至 45 分后两个独立进程竞争剩余 5 分，仅一个复杂识别成功；实际 Worker 的 `claimScoreJobById` 与 `markInterruptedBrokerJobFailed` 触发积分释放；迟到状态、重试、完成后取消及删除不能制造余额；API 200 分充值、幂等兑换、跨账户拒绝、原码继续登录及 500 MiB 存储均通过。测试完成后清理其随机 schema 与角色，不操作其他数据库。

`schema-version.ts` 更新为 26。SQLite 用 `PRAGMA user_version=26`；PostgreSQL 启动通过新增表检查确认已完成结构迁移，不把 PostgreSQL 写成持有 SQLite 的 user_version。

顺序必须是：**备份生产库 → owner 执行 SQL 升 26 → 更新 API＋Worker＋前端**。示例迁移参数（连接串由既有私有配置提供）：

