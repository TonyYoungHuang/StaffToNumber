# 简单识谱与复杂总谱工作台实施记录

本记录描述 2026-10-06 的本地实现与验证。生产网站尚未部署本轮变更；识别候选必须由用户复核后确认。

## 两个功能入口

| 功能 | 入口 | 每次识别积分 | 工作方式 |
| --- | --- | --- | --- |
| 简单乐谱 | `/scores/simple` | 1 | 原有工作台保留，使用快速识别与现有编辑、移调、播放、导出工具 |
| 复杂总谱 | `/scores/complex`；结果页 `/scores/:id/ensemble` | 5 | 原稿分层核对、跨页乐器整合、完整预览、按乐器/谱表/小节编辑、缺口定位与补录 |

API 配置 `OMR_SIMPLE_CREDIT_COST=1`、`OMR_COMPLEX_CREDIT_COST=5`。
客户端展示服务端报价，提交仅选择 `recognitionMode`，不能指定计费金额。
免费试用只允许简单模式；次卡和订阅按服务端额度判断。
额度在提交时事务预留，失败/取消释放，重试沿用原始模式、价格和付款来源。
新增乐器、人工补录和确认候选均不会再次收取识别积分。

## 复杂识别的完整性控制

1. 保留上传的所有页面。先生成独立的原稿页、系统、物理谱表与乐器组目录；识别结果不能反向决定原稿有几页或几个谱表。
2. 为页面记录原始尺寸、朝向和双向坐标变换；识别图与原稿坐标可追溯。
3. 按整页、系统、乐器组逐级处理。Audiveris 与 homr 真实引擎串行执行，局部失败只重试相应区域；执行次数、超时、取消和总预算有上限。
4. 依据来源乐器标签与谱表关系合并跨系统、跨页声部。名称或身份不明确时保留歧义，避免把布局推断包装成已核实的乐器身份。
5. 对照原稿目录检查页数、系统数、谱表覆盖、声部小节数量与时值。缺失区域保持静音同步占位和明确缺口，不填入虚构音符。
6. 保存候选、完整性报告、每次引擎尝试及区域原始 XML 证据。候选中的已识别内容可编辑；自动报告的状态与用户人工确认分别保存。

识别任务输出 `review-required` 或 `incomplete`，不会单凭引擎返回文件就自动宣布乐谱完整。
复杂候选确认前必须勾选原稿逐页/逐声部复核。确认记录 `manualReview`，保留原有缺口与自动判断。

## 预览、编辑与补录

- 完整总谱由 OSMD 渲染。通过 MusicXML 稳定 note ID 与 OSMD 实际 SourceNote/GraphicalNote 绑定，点击音符进入相应编辑位置；不依赖 SVG 顺序猜音符。
- 乐器、谱表、小节、音符导航使用 Smoosic 源码适配的选择器。原有工作台工具继续可用。
- alphaTab 提供 TAB/打击乐视图、音符选择和 SoundFont 播放。播放使用服务端统一 PlaybackDocument，已关联的五线谱与 TAB 不重复发声，鼓使用 MIDI 打击乐映射。
- 缺口和未归属谱表可以定位原图区域。用户可以新增缺失乐器并绑定来源谱表，创建待复核候选，再在现有编辑器补录。
- 新声部先建立与已知时间线对应的隐藏小节占位。插音和占位转音符会保留剩余空白时值；未填内容继续标记待复核。
- 手工鼓声部的插音和占位转音符生成无音高显示位置，鼓属性可直接编辑；未选择实际鼓声映射前保持静音，选择后使用 MIDI 第 10 通道。
- 手工编辑后的新候选保留原图引用；旧渲染图与旧 MusicXML 留在原版本，不冒充新内容。
- Enter 在音符按钮上正常选择目标，输入框和原生按钮保持其键盘行为；不会保存上一次选择。

## 保真导出

ScoreJSON 仍是编辑真相，MusicXML 原始文档作为保真交换层。
未编辑的 XML 节点保留；编辑只更新对应节点。支持 TAB 技术标记、延长歌词、弦调音、非建模演奏标记的保留。
已验证的同一音符标准谱/TAB对应关系共同更新音高、品位与时值，删除同步执行，播放只发声一次。

不能安全保留原时序的操作（例如带未建模 `forward` 时间间隙的结构变更、关联 TAB 的跨小节复制/移动及直接修改其声部/谱表/和弦位置/倚音结构）会明确拒绝并保持原版本，避免静默损坏。
保存候选和正式版本前执行保真导出预检，失败返回冲突，不会先写坏谱再让导出失败。

## 使用的项目与准备

实际集成 Audiveris、homr、Smoosic、alphaTab 与 OSMD，保留已有 MuseScore 导出。
源码快照、精确版本和许可证见 [第三方来源记录](../third_party/music-engines/README.md)。

Worker 配置在 `services/worker/.env.example`：

```dotenv
HOMR_PYTHON_COMMAND=python3
HOMR_SOURCE_DIR=../../third_party/music-engines/homr
COMPLEX_OMR_ADAPTER_PATH=python/complex_omr_adapter.py
COMPLEX_OMR_TIMEOUT_MS=900000
COMPLEX_OMR_ATTEMPT_TIMEOUT_MS=120000
COMPLEX_OMR_MAX_GROUP_ATTEMPTS=12
```

在部署使用的 CPU Python 环境中安装固定来源的 `homr[cpu]`，由管理员显式准备模型：

```sh
python services/worker/python/provision_complex_omr.py \
  --source-dir third_party/music-engines/homr \
  --download --manifest /path/to/private/complex-omr-models.json
```

去掉 `--download` 可离线检查。脚本验证源码 SHA 与六个模型 SHA-256。
付费识别路径要求模型已存在，不在任务中下载模型。生产启用前应在目标服务器校验模型、CPU/RAM、临时磁盘和任务预算。
当前重引擎门禁在单个 Worker 进程内协调；同一主机先使用一个 Worker 进程，完成实际资源测试后再评估多进程。
真实引擎准备与完整性测试详见 [Worker 配置说明](../services/worker/python/README.md) 和 [识别验收记录](../services/worker/python/QUALIFICATION.md)。

## 已验证结果与边界

- SQLite 与隔离 PostgreSQL 的双进程额度竞争：最后 5 分只能提交一笔复杂任务，另一笔拒绝；失败、取消和重试行为已覆盖。
- 完整预览实际绑定 440 个唯一可定位的主谱音符；Enter 选择不发送保存请求，1.25 倍缩放和 390px 宽度仍保持定位。
- 548 音符的完整谱例，重新导出和单音修改后再导出均保留 10 处调弦、92 处弦号/品位、10 处 hammer-on、4 处 pull-off、2 处 bend、6 处歌词延长线。导出通过本地 MusicXML 4.0 XSD 校验。
- 实际复杂原稿包含两个系统、16 个物理谱表、4 个 TAB 谱表。双引擎识别与来源归组得到 6 个乐器声部、每声部 8 小节；生成 XML 通过 XSD，仍报告 38 项结构/识别缺口，不能据此称音符已全部准确。
- 两页原创 PDF 双引擎验证保留两页，生成两个小节、8 个事件并通过 XSD；无唯一乐器标签时跨页身份继续标记待核实。
- 四个朝向的实际图像测试覆盖 0/90/180/270 度并记录坐标变换。

自动 TAB 数字、复杂鼓谱、低质量印刷与无乐器标签仍需要人工核对/补录。
没有可靠弦号的 TAB 音符在专项视图提供可选择列表和说明，原始 MusicXML 与完整总谱保持保留，不猜弦号。
完整性控制保证原稿和缺口可追踪、避免静默丢谱；它不等同于任意输入的音符识别准确率保证。

本地回归包含保真编辑/播放、原图引用延续、缺失声部补录、候选确认、额度生命周期、复杂识别预算/取消与引擎并发门禁。外部 Redis 测试在无对应服务时明确跳过。
复杂编辑专项界面文案提供英文、简体中文和日语；其余六种界面语言暂使用英文回退，原有工具的九语文案保留。免费结构预检、模式选择与收费确认另提供九语文案，见 [免费预检实现记录](./score-structure-preflight-2026-10-06.md)。

最终构建：shared、API、Worker 与 Next.js 应用的正式构建均通过；正式构建包含三个新增路由。
最终前端单元测试 152/152 通过，保真/手工补录专项 15/15 通过；其余乐谱编辑/交换/播放相关 60 项回归通过。
浏览器验收覆盖两种导入、完整预览定位、原生 Enter、缩放/隐藏切换、实际 TAB 音符点击、同版本统一 MIDI、SoundFont 资源、属性保存、原图缺口、新增声部、人工确认与 390px 布局。
